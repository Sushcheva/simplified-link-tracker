# Выпуск релиза и проверки в GitHub Actions

Релиз — это конкретная версия приложения вместе с конфигурацией запуска.
В проекте выпуск запускается Git-тегом вида `v1.2.0`. Версия тега должна совпадать
с версией в корневом `pom.xml` и родительской версией обоих модулей.

## Что выполняет pipeline

Файл `.github/workflows/verify.yml` запускается при изменении `main`, pull request,
ручном запуске и отправке тега `v*`.

1. Runner Ubuntu 24.04 устанавливает Temurin Java 25 и запускает PostgreSQL 16.4.
2. Maven собирает модули, выполняет 19 unit-тестов и 10 интеграционных тестов
   с настоящей PostgreSQL. Внешние API для этих сценариев не требуются.
3. Dockerfile, стадия `prebuilt`, помещает проверенный JAR в образ без повторной
   компиляции. Обычная сборка Dockerfile по-прежнему умеет собрать исходники сама.
4. `verify_runtime.py` создаёт отдельную сеть, PostgreSQL 16.4, локальный HTTP-fixture
   и контейнеры приложения. Проверяет приватный CRUD и вход, нагрузку на одну/две
   web-реплики, два worker, старт JVM, SIGTERM с текущим запросом и SIGKILL с откатом
   транзакции. Временные контейнеры удаляются даже при ошибке.
5. Проверяются Compose и подготовка Kubernetes-манифестов. Логи, JUnit-результаты
   и `runtime.json` сохраняются в артефактах Actions на 30 дней.
6. Только для тега после успешных проверок запускается отдельная задача публикации.
   Она получает **тот же проверенный образ** через `docker save/load`, отправляет его
   в GHCR, получает digest и подставляет его в манифесты. Повторной сборки нет.
7. Создаётся черновик GitHub Release, прикладываются все файлы, затем релиз публикуется.
   Для репозитория включена неизменяемость релизов: опубликованный тег и вложения
   защищены от изменения. Контрольные суммы дополнительно фиксируют содержимое файлов.

Обычная проверка имеет `contents: read`. Право `contents: write` и `packages: write`
получает только задача публикации тега. Используется временный `GITHUB_TOKEN`,
личный токен в настройках проекта не требуется. Actions закреплены на SHA коммитов.
Pipeline **не развёртывает приложение в рабочем кластере**: он поднимает тестовое
окружение и выпускает готовые артефакты. Доступа к Docker Desktop пользователя у него нет.

## Как выпустить следующую версию

Обновить версии в `pom.xml`, `frontend/pom.xml`, `scrapper/pom.xml`, а также значение
`RELEASE_VERSION` в `.env.example` и значение по умолчанию в Compose. Обновить описание
изменений в README/отчёте, зафиксировать их и отправить в `main`. Дождаться успешного
pipeline для этого коммита в разделе Actions.

Например, для следующей версии `1.2.1`:

```bash
git status --short
git tag -a v1.2.1 -m "Release 1.2.1"
git push origin v1.2.1
```

Рабочее дерево перед тегом должно быть чистым. Создавать тег следует на проверенном
коммите. Pipeline повторно проверит помеченную версию и опубликует её только при успехе.
Не нужно вручную пересобирать образ, создавать GitHub Release или прикладывать файлы.

Если проверка упала до публикации, посмотреть ошибку в Actions. Исправление кода требует
нового коммита и нового номера версии: уже опубликованные версии не перемещаются.
Если публикация остановилась на черновике, сначала проверить его и логи. Скрипт
отказывается перезаписывать существующий релиз; он не удаляет чужие файлы автоматически.

## Что находится в релизе

| Файл | Назначение |
|---|---|
| `scrapper.jar` | Проверенное исполняемое приложение |
| `simplified-link-tracker-<версия>.zip` | Исходники, README и `Отчёт.md` для сдачи |
| `deployment.zip` | Готовые Kubernetes-манифесты с образом по digest |
| `release.json` | Версия, коммит, digest, платформа, имя Secret, ссылка на проверку, хеши артефактов |
| `runtime.json` | Реальные измерения нагрузки и жизненного цикла в CI |
| `SHA256SUMS` | Контрольные суммы вложений |

После скачивания всех перечисленных файлов в один каталог:

```bash
shasum -a 256 -c SHA256SUMS
```

На Linux вместо `shasum -a 256` можно использовать `sha256sum`.
Контейнер хранится в `ghcr.io/sushcheva/simplified-link-tracker`. Для развёртывания
нужно брать значение `image` из `release.json`, содержащее `@sha256:...`.
Тег удобен для поиска; digest однозначно определяет содержимое. Текущий pipeline
собирает платформу `linux/amd64`.

## Конфигурация и секреты

ConfigMap получает уникальное имя релиза и `immutable: true`. Манифесты ссылаются
на отдельный Secret, например `link-tracker-secrets-v1-2-0`. При запуске оператор
создаёт его из `.env.k8s` и устанавливает `immutable: true`, как описано в Kubernetes-гайде.
Реальные значения паролей и токенов **не входят** в исходники, Actions-артефакты или релиз.

Изменение конфигурации требует нового комплекта развёртывания с новым идентификатором.
Для конфигурационного релиза можно использовать прежний digest без пересборки образа.
Чтобы откатить развёртывание, должны оставаться доступны его образ, ConfigMap и Secret,
а текущая схема PostgreSQL должна быть совместима с выбранной версией приложения.
Миграции БД не откатываются командой `rollout undo`.

## Как повторить нагрузку и замеры локально

Нужны Docker, Python 3, JDK 25 и Maven Wrapper. Используется только временная БД.

```bash
./mvnw --batch-mode --no-transfer-progress package
docker build --target prebuilt -t simplified-link-tracker:verification .
python3 scripts/verify_runtime.py --image simplified-link-tracker:verification \
  --duration 20 --clients 4,16 --output .local/verification
```

В каждой нагрузочной точке 70% запросов читают список, 20% — историю, 10% изменяют
свою ссылку. Клиент сохраняет HTTP/1.1-соединения и передаёт cookie/CSRF. Регистрация
выполняется до измерения. Число клиентов фиксировано; каждый отправляет следующий
запрос после ответа, без паузы. Это закрытая модель нагрузки, не обещание выдержать
произвольную входящую частоту. Запросы распределяет сам тестовый клиент; Kubernetes
Service и сетевой балансировщик в этом измерении не участвуют.

Каждый web-контейнер ограничен 1 CPU и 768 MiB, JVM — `-Xmx256m`, пул БД — пять
соединений. Сценарии сохраняют длительность, число запросов, RPS, p50/p95/p99,
ошибки и распределение успешных ответов между репликами. Перед измерениями есть
пятисекундный прогрев. Результаты зависят от машины и фоновой нагрузки; линейный рост
скорости при добавлении процессов не гарантируется.

Старт измеряется от `docker start` до успешной readiness-проверки. Это запуск новой
JVM с уже скачанным образом, без очистки файлового кэша хоста. SIGTERM измеряется
до завершения контейнера: отдельно в покое и во время трёхсекундной проверки ссылки.
После SIGKILL проверяется отсутствие частично сохранённого события, возможность
повторить проверку на другой реплике и отсутствие дубля при ещё одном повторе.
Сессия также должна сохраниться после штатного перезапуска web-процесса.

Эти проверки подтверждают конкретные сценарии на небольшом учебном стенде.
Они не заменяют длительный нагрузочный прогон, проверку Kubernetes rollout,
отказ базы данных и измерения в реальном production-окружении.

Результаты успешного прогона 2 октября 2026 года сохранены в
[docs/verification](verification/README.md) и подробно разобраны в отчёте.
