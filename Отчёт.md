# Отчёт по первому домашнему заданию

## Доменная область

Simplified Link Tracker — приложение для хранения ссылок и отслеживания активности
в репозиториях GitHub и вопросах Stack Overflow. Оно помогает собрать интересующие
ресурсы в личную коллекцию и увидеть, для каких из них обнаружены изменения.

Пользователь регистрируется по email и паролю, входит в приложение, добавляет HTTPS-ссылку, задаёт название
и теги. В коллекции доступны поиск по названию и адресу, фильтрация по тегу,
редактирование и удаление записей. Автоматическое отслеживание можно приостановить
для отдельной ссылки, а проверку вручную — запустить кнопкой «Проверить сейчас».
Лента показывает последние 20 обнаруженных обновлений.

Мониторинг сравнивает время изменения ресурса, полученное от внешнего API, с сохранённой
отметкой. Для GitHub используется поле `updated_at` репозитория, для Stack Overflow —
`last_activity_date` вопроса. Первая успешная проверка устанавливает точку отсчёта.
При последующем увеличении отметки приложение сохраняет событие в ленте. Если между
проверками произошло несколько действий, они могут дать одно обнаруженное обновление.

Коллекция и лента принадлежат конкретному пользователю. Без входа доступны формы
авторизации и служебные проверки состояния. Запросы к чужой ссылке возвращают 404,
включая её изменение, удаление, ручную проверку и чтение истории. Выход завершает
текущую сессию. Проект предназначен прежде всего для локального учебного использования.

## Стек и компоненты

| Технология | Назначение |
|---|---|
| Java 25, Spring Boot 4.0.2 | Серверное приложение и управление его компонентами |
| Maven Wrapper 3.9.12 | Общая сборка модулей, загрузка зависимостей и запуск тестов |
| HTML, CSS, JavaScript | Интерфейс и обработка действий в браузере |
| Spring Security 7.0.2 | Вход по паролю, CSRF-защита, проверка доступа, BCrypt |
| Spring Session JDBC 4.0.1 | Хранение сессий в PostgreSQL, общий вход для web-реплик |
| Spring MVC | REST API по HTTP/1.1 и выдача файлов интерфейса |
| Spring RestClient и HTTP-интерфейсы | Обращение к API GitHub и Stack Exchange |
| Spring JDBC / JdbcClient | Выполнение параметризованных SQL-запросов |
| PostgreSQL 16.4 | Постоянное хранилище в Docker Compose и Testcontainers |
| Liquibase | Применение изменений схемы БД |
| Spring Boot Actuator | Проверка состояния приложения и подключения к БД |
| JUnit, Mockito, Testcontainers | Модульные и интеграционные тесты |
| Docker, Docker Compose | Сборка образа и описание локального окружения |
| Kubernetes в Docker Desktop | Подготовленные манифесты БД, web, worker и миграций; гайд локального развёртывания |

**Модуль `frontend`.** Содержит `index.html`, `styles.css` и `app.js` в каталоге
`src/main/resources/META-INF/resources`. HTML определяет страницу и формы, CSS —
оформление, JavaScript — запросы к серверу и отображение ответов. Через интерфейс
пользователь регистрируется, входит, выполняет CRUD, управляет проверками и читает ленту. Браузер обращается
к относительным адресам `/api/auth/*`, `/api/links` и `/api/updates`, поэтому отдельная настройка
адреса бэкенда ему не нужна.

**Модуль `scrapper`.** Содержит серверную логику. Пакет `controller` принимает
HTTP-запросы, пакет `auth` отвечает за аккаунты, сессии и правила Spring Security,
`service` реализует правила работы со ссылками и транзакции,
`repository` выполняет SQL. Пакет `client` содержит HTTP-клиенты внешних сервисов.
В `scheduler` находится планировщик, а в `scheduler/checker` — обработчики GitHub
и Stack Overflow. Модели данных находятся в `domain`, форматы запросов и страницы
результатов — в `dto`, настройки — в `properties`, обработка ошибок — в `exception`.

При сборке `frontend` становится зависимостью `scrapper`. Итоговый исполняемый JAR
содержит бэкенд и файлы интерфейса. Java-код работает на сервере, JavaScript — в браузере.
Два Maven-модуля образуют одно клиент-серверное приложение.

**PostgreSQL и процесс `migrate`.** База данных хранит аккаунты, коллекции, сессии
и результаты мониторинга. Схема описана SQL-файлами и журналом миграций Liquibase в ресурсах
`scrapper`. В Compose сервис `migrate` запускает тот же образ приложения, применяет
миграции и завершает работу. Затем запускается сервис `app`. Постоянно работают
`app` и `postgresql`; `migrate` является разовой задачей.

**Каталог `scripts`.** Содержит проверку HTTP API, локальные тестовые ответы внешних
сервисов, запуск изолированного проверочного окружения и упаковку исходников.
Это вспомогательные инструменты разработки. Скрипт `render_k8s.py` готовит
манифесты именованного Kubernetes-релиза. Шаблоны находятся в `k8s/`, порядок запуска —
в [гайде по Kubernetes](docs/Kubernetes.md).

Взаимодействие компонентов при добавлении ссылки:

1. После входа браузер отправляет JSON в `POST /api/links` вместе с cookie и CSRF-токеном.
2. Spring Security проверяет сессию и токен. `ScrapperController` получает ID пользователя
   из проверенного principal и проверяет ограничения полей.
3. `LinkService` использует `LinkUrlNormalizer` для проверки и нормализации адреса.
4. `JdbcLinkRepository` сохраняет ссылку в PostgreSQL с `owner_id` текущего пользователя.
5. Сервер возвращает созданную запись, интерфейс обновляет коллекцию.

Мониторинг запускается независимо от открытой страницы: `LinkUpdaterScheduler`
передаёт работу `LinkMonitorService`, обработчик ресурса вызывает внешний API,
а результат сохраняется в PostgreSQL. Браузер получает ленту через `GET /api/updates`.
При видимой вкладке и закрытой форме интерфейс обновляет данные каждые 30 секунд.

## Основные сущности

**Пользователь — таблица `users`.** Поля `id`, `email`, `password_hash`, `created_at`.
Email хранится в нижнем регистре, ограничен 254 символами и уникален. Пароль
не сохраняется открытым текстом: `BCryptPasswordEncoder` вычисляет хеш со случайной
солью и стоимостью 12. При регистрации требуется 10–64 символа и максимум 72 байта
UTF-8. Ответы API содержат только ID и email. Один пользователь владеет многими ссылками.

**Сессия — технические таблицы `spring_session` и `spring_session_attributes`.**
Хранят идентификатор, сроки действия и сериализованные атрибуты Spring Security.
Cookie `LINK_TRACKER_SESSION` содержит случайный идентификатор, имеет `HttpOnly`,
`SameSite=Lax` и настраиваемый `Secure`. Срок бездействия задаётся `SESSION_TIMEOUT`.
Сессия — техническое состояние входа, а не сущность мониторинга. После выхода она
удаляется из БД; разные web-процессы проверяют вход по одним и тем же таблицам.

**Отслеживаемая ссылка — таблица `links`.** Представляет ресурс, активность которого
интересует пользователя. Владелец определяется сервером из сессии, а не из входного JSON.
Один URL может находиться в независимых коллекциях разных пользователей.

| Поле | Смысл |
|---|---|
| `id` | Идентификатор записи |
| `owner_id` | Владелец, внешний ключ на `users.id` |
| `url` | Нормализованный адрес; уникален в пределах владельца благодаря `(owner_id, url)` |
| `title` | Название, заданное пользователем |
| `tags` | Массив тегов в формате JSONB |
| `enabled` | Разрешена ли автоматическая проверка |
| `created_at` | Время создания записи |
| `last_check_time` | Время последней завершённой проверки, в том числе неуспешной |
| `last_seen_at` | Последняя принятая временная отметка внешнего ресурса |
| `next_check_at` | Момент, начиная с которого планировщик может взять ссылку |
| `last_error` | Ошибка последней проверки; при успешной проверке очищается |

**Обновление — таблица `link_updates`.** Хранит обнаруженное изменение: `id`,
`link_id`, описание `description`, время изменения ресурса `remote_updated_at`
и время обнаружения `detected_at`. Одной ссылке соответствует несколько обновлений.
Внешний ключ с `ON DELETE CASCADE` удаляет историю вместе со ссылкой.
Ограничение `UNIQUE (link_id, remote_updated_at)` препятствует повторному сохранению
одного изменения.

**Тег.** Текстовая метка для группировки ссылок. Хранится в массиве `links.tags`;
отдельной таблицы тегов нет. При сохранении пробелы по краям удаляются, повторы
объединяются. Фильтр выбирает ссылки, содержащие заданный тег.

Полный CRUD реализован для отслеживаемой ссылки и доступен через веб-интерфейс:

| Операция | HTTP API | Результат |
|---|---|---|
| Create — создание | `POST /api/links` | Новая запись с URL, названием, тегами и признаком отслеживания |
| Read — чтение | `GET /api/links`, `GET /api/links/{id}` | Список с поиском и фильтрацией либо одна запись |
| Update — изменение | `PUT /api/links/{id}` | Изменение URL, названия, тегов и `enabled` |
| Delete — удаление | `DELETE /api/links/{id}` | Удаление ссылки и связанной истории |

История создаётся мониторингом и доступна для чтения. При смене URL история записи
очищается, а первая успешная проверка нового адреса устанавливает его исходную отметку.
Схема и ограничения находятся в
`scrapper/src/main/resources/migrations/001-initial-schema.sql` и
`002-accounts-and-sessions.sql`. Вторая миграция оставляет ранее созданные ссылки
без владельца: они скрыты от пользователей и не проверяются планировщиком.
Администратор явно назначает владельца отдельной командой `assign-legacy`.

## Соответствие 12 факторам

### I. Кодовая база

**Смысл.** Исходники приложения должны иметь одну историю в системе контроля версий.
Разные развёртывания используют версии этой кодовой базы. [Описание фактора I](https://12factor.net/ru/codebase).

**Реализация.** Оба модуля, миграции, настройки сборки, скрипты и документация находятся
в одном каталоге. Корневой `pom.xml` объединяет `frontend` и `scrapper`, поэтому
их можно фиксировать и выпускать совместно. Отдельное окружение задаётся конфигурацией,
ему не нужна собственная копия исходников с изменёнными адресами БД.

`.gitignore` исключает реальные `.env`, результаты сборки, журналы, архивы и настройки
IDE. В системе контроля версий должны храниться исходники и `.env.example` с образцом
настроек. Это позволяет связать версию приложения с определённым коммитом.

**Оценка: реализован.** Исходники ведутся в одном Git-репозитории,
связанном через `origin` с
[Sushcheva/simplified-link-tracker](https://github.com/Sushcheva/simplified-link-tracker).
Модули, миграции, документация и Kubernetes-шаблоны фиксируются совместно.
Команда `git rev-parse HEAD` определяет текущую версию исходников. При выпуске
развёртывания необходимо сохранять связь релиза с этим коммитом.

### II. Зависимости

**Смысл.** Нужные библиотеки и среда выполнения должны быть объявлены явно.
Приложение не должно зависеть от случайно установленных библиотек на машине.
[Описание фактора II](https://12factor.net/ru/dependencies).

**Реализация.** Зависимости серверного модуля перечислены в `scrapper/pom.xml`:
Spring MVC, JDBC, RestClient, Validation, Liquibase, Actuator и драйвер PostgreSQL.
Зависимость от `frontend` объявлена там же. Версии библиотек управляются родительским
POM Spring Boot 4.0.2, версия Java указана в корневом POM. Maven Wrapper фиксирует
Maven 3.9.12 в `.mvn/wrapper/maven-wrapper.properties`.

Dockerfile описывает сборку на JDK 25 и запуск на JRE 25. В исполняемый JAR входят
необходимые Java-библиотеки и файлы интерфейса. Фронтенд использует браузерные API
и не загружает библиотеки, шрифты или скрипты с CDN. Python 3 и локальные инструменты
PostgreSQL нужны только для соответствующих проверочных скриптов; эти требования
перечислены в README.

**Оценка: основной принцип реализован.** Состав зависимостей и способ их получения
определены проектом. Теги образов Java `25-jdk` и `25-jre` допускают обновление
содержимого, поэтому сборка не заявляется как побайтово воспроизводимая.
Закрепление образов по digest повысит воспроизводимость. Это дополнительное уточнение
к управлению зависимостями, а не свойство, которое уже обеспечено текущим Dockerfile.

### III. Конфигурация

**Смысл.** Параметры конкретного развёртывания передаются через окружение.
Один собранный артефакт должен работать с разными настройками.
[Описание фактора III](https://12factor.net/ru/config).

**Реализация.** `application.yaml` связывает настройки Spring Boot с переменными
окружения: `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD`, `PORT`,
`GITHUB_API_URL`, `STACKOVERFLOW_API_URL`, `GITHUB_TOKEN`, параметрами планировщика,
таймаутами и уровнем логирования. `SESSION_TIMEOUT` и `SESSION_COOKIE_SECURE` задают
срок сессии и требование HTTPS для cookie. В локальном HTTP-сценарии `Secure` отключён;
при публикации за TLS-прокси его нужно включить через окружение. Например, подключение к другой PostgreSQL задаётся
через переменные БД без изменения Java-кода и пересборки JAR.

Рабочий пароль не задан в исходниках. `.env.example` содержит образец настроек,
а реальные `.env` исключены из Git, контекста Docker-сборки и исходного архива.
При контейнерном запуске Compose использует `.env` для подстановки значений, затем
передаёт перечисленные в `environment` переменные процессу. При прямом запуске JAR
их нужно экспортировать в оболочке.

Для Kubernetes предусмотрены неизменяемый ConfigMap с именем релиза и Secret
`link-tracker-secrets-<релиз>`. В контейнеры значения передаются через `envFrom`.
Секрет создаётся пользователем из игнорируемого файла `.env.k8s` и закрепляется
как `immutable: true`. Значения не публикуются; новая конфигурация получает новое имя.

**Оценка: реализован.** Настройки отделены от артефакта приложения. При этом запись
произвольной переменной в `.env` не передаёт её автоматически в контейнер:
дополнительные параметры, например `LOG_LEVEL` или `API_READ_TIMEOUT`, нужно включить
в `environment` либо в Compose override. Сам Java-процесс их поддерживает.

### IV. Внешние службы

**Смысл.** База данных и другие сетевые службы рассматриваются как подключаемые
ресурсы. Их расположение и доступ задаются конфигурацией.
[Описание фактора IV](https://12factor.net/ru/backing-services).

**Реализация.** Приложение использует PostgreSQL через JDBC, GitHub и Stack Exchange —
через HTTP-клиенты. Адрес и учётные данные БД поступают из окружения. Для переноса
на другой сервер PostgreSQL с подготовленной схемой достаточно изменить параметры
подключения. Данные базы в Compose находятся в отдельном томе `postgres-data`;
пересоздание контейнера приложения не удаляет этот том.

Базовые адреса внешних API задаются свойствами `GITHUB_API_URL` и
`STACKOVERFLOW_API_URL`, которые читает `ClientConfiguration`. В изолированной
проверке эти адреса указывают на локальный HTTP-сервис из `scripts/api_fixture.py`.
Таким образом, тестирование использует тот же механизм подключения ресурсов.

**Оценка: реализован.** Экземпляры служб с совместимым протоколом и схемой можно
заменять конфигурацией. PostgreSQL использует специфичные возможности, включая JSONB
и блокировки строк: замена СУБД на другой продукт потребует изменения кода.
API-клиенты также ожидают конкретные контракты GitHub и Stack Exchange.
Фактор не предполагает автоматической поддержки произвольной СУБД или произвольного API.

### V. Сборка, релиз, выполнение

**Смысл.** Сборка создаёт артефакт, релиз связывает его с конфигурацией, выполнение
запускает процессы этого релиза. Релизу нужен уникальный идентификатор и неизменяемое
содержимое. [Описание фактора V](https://12factor.net/ru/build-release-run).

**Реализация.** Maven компилирует оба модуля и создаёт `scrapper/target/scrapper.jar`.
GitHub Actions проверяет этот JAR и помещает его в стадию `prebuilt` Dockerfile.
Полученный образ проходит HTTP-, нагрузочные и lifecycle-проверки. При выпуске
используется именно этот образ через `docker save/load`, повторной компиляции нет.
Контейнер запускает `java -jar /app/app.jar`; сборка при старте не выполняется.

Релиз запускается тегом `v<версия>`, совпадающим с Maven-версией. Отдельная задача
публикует образ в GHCR и фиксирует его digest. Генератор `render_k8s.py` связывает
один образ с web, worker и миграциями, создаёт неизменяемый ConfigMap с именем
релиза и ссылки на отдельный Secret с версией. Оператор создаёт этот Secret при
развёртывании и сохраняет прежние версии для отката. Пароли в релиз не входят.

GitHub Release содержит исходники с отчётом, проверенный JAR, `deployment.zip`,
`runtime.json`, `release.json` и `SHA256SUMS`. Метаданные связывают тег, коммит,
образ, конфигурацию, имя Secret и запуск CI. Для репозитория включены immutable
releases: скрипт сначала прикладывает файлы к черновику и только затем публикует
релиз, фиксируя его тег и вложения. Порядок описан в [гайде по релизам](docs/Releases.md).

**Оценка: механизм сборки, выпуска и запуска реализован.** Релиз приложения имеет
фиксированный состав; настройки конкретного окружения задаются при развёртывании.
Нужно сохранять соответствующий Secret в кластере или защищённом хранилище оператора.
Секреты рабочего окружения и Kubernetes-развёртывание автоматически не создаются.
Локальные Docker-теги остаются изменяемыми, поэтому готовые релизы используют digest.
Откат в кластере ещё не проверен: возврат старого образа допустим только с совместимой
схемой БД и сохранённой конфигурацией; `rollout undo` не отменяет миграции.

### VI. Процессы

**Смысл.** Процесс приложения не должен быть единственным местом хранения данных,
которые понадобятся следующему запросу или после перезапуска.
[Описание фактора VI](https://12factor.net/ru/processes).

**Реализация.** Ссылки, теги, история, ошибки и расписание следующих проверок хранятся
в PostgreSQL. Методы `JdbcLinkRepository` читают и изменяют эти записи напрямую.
Аккаунты и сессии также находятся в PostgreSQL: `AccountService` использует JDBC,
а Spring Session сохраняет сессию между запросами в `spring_session` и
`spring_session_attributes`. Процесс не является единственным хранилищем
пользовательских данных, сессий или очереди проверок.

Планировщик при каждом проходе выбирает из БД включённые ссылки с наступившим
`next_check_at`. После перезапуска ему не требуется восстанавливать собственную
локальную очередь. Флаг `stopping` в `LinkUpdaterScheduler` относится только
к завершению текущего процесса и не содержит пользовательских данных.

В браузере находятся выбранный фильтр, открытая форма и полученный список.
Это состояние интерфейса; сохранённые записи загружаются с сервера и находятся в БД.
Cookie содержит только идентификатор, пароль в локальном хранилище браузера не
сохраняется. Другой HTTP-экземпляр с тем же релизом и БД способен обработать следующий
запрос с той же cookie. Локальная проверка двух JVM подтвердила чтение аккаунта и
изменение ссылки через второй сервер; выход через первый закрыл доступ на втором.

**Оценка: реализован.** Перезапуск процесса не уничтожает уже зафиксированные данные.
Долговечность хранилища обеспечивается PostgreSQL и сохранением её тома.
Незавершённая транзакция может быть отменена, после чего проверка будет доступна снова.

### VII. Привязка портов

**Смысл.** Веб-приложение само предоставляет сетевой сервис через порт и содержит
необходимый HTTP-сервер в своей среде выполнения.
[Описание фактора VII](https://12factor.net/ru/port-binding).

**Реализация.** Spring Boot запускает встроенный веб-сервер вместе с приложением.
Через один порт доступны HTML, CSS, JavaScript, REST API и служебные health-маршруты.
Java-процесс слушает `PORT`, по умолчанию 8080. Отдельная установка и настройка
внешнего сервера приложений для запуска JAR не требуется.

В Compose внутренний порт 8080 опубликован как `127.0.0.1:APP_PORT`.
Переменная `APP_PORT` управляет адресом доступа с компьютера, а `PORT` — портом
самого Java-процесса. Текущий Compose оставляет внутренний порт равным 8080.
HTTP/2 отключён свойством `server.http2.enabled=false`; браузер и API могут
взаимодействовать по HTTP/1.1.

**Оценка: реализован для веб-процесса.** Перед приложением можно поставить
балансировщик, направляющий запросы на его HTTP-порт. Worker и миграции запускаются
с `SPRING_MAIN_WEB_APPLICATION_TYPE=none`, поскольку не предоставляют веб-сервис.
Отсутствие порта у таких процессов соответствует их назначению.

### VIII. Параллелизм

**Смысл.** Увеличение нагрузки обрабатывается запуском дополнительных процессов.
HTTP-обработку и фоновую работу должно быть возможно масштабировать по отдельности.
[Описание фактора VIII](https://12factor.net/ru/concurrency).

**Реализация.** Один JAR поддерживает веб-процесс с `SCHEDULER_ENABLED=false`
и фоновый процесс с `SPRING_MAIN_WEB_APPLICATION_TYPE=none`,
`SCHEDULER_ENABLED=true`. Значение `APP_MODE=worker` обозначает назначение
запуска; отключение HTTP и включение проверок определяют два указанных свойства.
Команды приведены в README. Экземпляры используют общую PostgreSQL; при прямом
запуске на одном компьютере веб-процессам задают разные порты.

Метод `lockNextDue()` выбирает ссылку через `FOR UPDATE SKIP LOCKED`.
Пока один процесс проверяет её, другие пропускают занятую строку и могут выбрать
другие ссылки. После проверки `next_check_at` переносится вперёд. Сохранение события
и отметки выполняется в одной транзакции, уникальная пара
`(link_id, remote_updated_at)` защищает историю от повторов.
Контейнер запускает Java напрямую; перезапусками управляет Docker.

Манифесты Kubernetes описывают два web Pod за Service и отдельный worker Deployment.
Для каждого типа процессов число реплик можно изменять независимо.
Шаблоны находятся в `k8s/web.yaml` и `k8s/worker.yaml`; команды масштабирования
приведены в гайде.

**Оценка: реализован и проверен на нескольких процессах.** В успешном CI-прогоне
2 октября 2026 года сравнивались одна и две web-реплики на общей PostgreSQL 16.4.
При 16 параллельных клиентах измерено 622,46 и 848,79 запросов/с соответственно,
p95 — 71,25 и 52,93 мс; ошибок не было. Два worker обрабатывали восемь ссылок:
оба процесса выполняли работу, наблюдались два одновременных внешних запроса,
для каждой ссылки сохранилось ровно одно событие изменения.

Условия и все точки приведены в разделе «Проверки», исходные данные — в
[JSON измерений](docs/verification/runtime-20261002.json). Запросы распределяет
тестовый клиент; это проверка модели процессов без Kubernetes Service.
Нагрузочный сценарий использует небольшие коллекции и не измеряет предел всей системы.
Реальное масштабирование в Kubernetes, работа балансировщика и длительная нагрузка
ещё требуют проверки. При увеличении числа worker нужно учитывать лимиты внешних API.
Compose описывает один `app` с фиксированным опубликованным портом; для независимых
реплик предназначены Kubernetes-манифесты или отдельные контейнерные запуски.

### IX. Утилизируемость

**Смысл.** Процесс должен запускаться с небольшими накладными расходами, корректно
завершать работу по сигналу и сохранять согласованность данных при аварийной остановке.
[Описание фактора IX](https://12factor.net/ru/disposability).

**Реализация.** Обычный запуск использует готовый JAR; компиляция и миграции вынесены
в отдельные шаги. В `application.yaml` включён `server.shutdown=graceful`,
задан лимит 20 секунд на фазу завершения Spring и ожидание завершения планировщика
до 15 секунд. Compose даёт контейнеру 30 секунд через `stop_grace_period`.
Exec-форма `ENTRYPOINT` запускает Java без промежуточной оболочки.

При закрытии Spring-контекста планировщик устанавливает `stopping` и перестаёт
брать следующие ссылки в цикле. Для внешнего HTTP-клиента настроены таймауты
подключения 2 секунды и чтения 5 секунд. Результат проверки записывается транзакционно:
событие и временная отметка фиксируются вместе.

Если процесс аварийно завершится, после обнаружения потери соединения PostgreSQL
откатит незавершённую транзакцию и снимет её блокировку. Ссылка с наступившим сроком
станет доступна другому процессу. Повторное сохранение той же отметки не создаст
дублирующее событие.

В Kubernetes-манифестах для web предусмотрены startup-, liveness- и readiness-probes,
а контейнерам приложения даётся 60 секунд на завершение.
Worker запускается без HTTP-сервера и без HTTP-probes; его работу проверяют по логам.

**Оценка: механизмы реализованы и проверены на контейнерном стенде.** Четыре запуска
web JVM до readiness заняли 11,174–12,577 с. Это старт с готовым образом, без скачивания
и без очистки файлового кэша хоста. SIGTERM завершил web без активного запроса за
0,230 с, во время запроса с задержкой внешнего API 3 с — за 3,092 с; клиент получил
успешный ответ. Сессия сохранилась после штатного перезапуска. Остановка worker
по SIGTERM заняла 0,281 с; этот замер сам по себе не доказывает завершение каждой
текущей фоновой задачи.

При SIGKILL во время проверки ссылки HTTP-запрос оборвался, а другая реплика увидела
предыдущее согласованное состояние без частичного события. Повторная проверка через
работающую реплику завершилась за 0,124 с и создала одно событие; ещё один повтор
не создал дубль. Время 0,124 с измеряет саму повторную операцию после доступности
тестового API, а не полный срок обнаружения и устранения аварии.

Подробные условия и исходные замеры сохранены в разделе «Проверки». Они не задают
гарантированного верхнего предела: SQL-задержки, недоступность БД и зависание сети
проверяются отдельно. Общий лимит завершения контейнера может прервать затянувшуюся
работу; при изменении таймаутов нужно согласовать их с лимитами завершения.

### X. Паритет окружений

**Смысл.** Среды разработки, проверки и эксплуатации должны быть близки
по инструментам; изменения должны быстро доходить до запуска, а разработчик —
участвовать в проверке развёрнутой версии.
[Описание фактора X](https://12factor.net/ru/dev-prod-parity).

**Реализация.** Compose, Kubernetes StatefulSet и GitHub Actions используют PostgreSQL
16.4. Профиль Maven `integration` работает с настоящей PostgreSQL; в CI адрес
контейнерной БД передаётся через `TEST_DATABASE_URL`, локально профиль умеет создавать
её через Testcontainers. В успешном CI проверены JSONB, ограничения, блокировки,
сессии, авторизация и CRUD на объявленной версии СУБД. Подмена на H2 не используется.

`.github/workflows/verify.yml` запускается при push в `main`, pull request, вручную
и по тегу. Runner Ubuntu 24.04 использует Temurin Java 25. После Maven-проверок
собранный JAR помещается в образ JRE 25 и действительно запускается вместе с
PostgreSQL 16.4 для HTTP-, нагрузочных и lifecycle-проверок. Миграции выполняются
разовой командой того же образа. Результаты и логи сохраняются как артефакты Actions.
После успешной проверки тега задача релиза публикует тот же образ; конфигурация
окружения подключается при запуске. Рабочие пароли для CI не нужны.

**Оценка: технический паритет сборки и тестового окружения подтверждён; эксплуатационный
паритет требует реального развёртывания.** Java 25 и PostgreSQL 16.4 совпадают
с конфигурацией поставки. Успешный CI-прогон связан с конкретным коммитом, проверки
автоматически повторяются при изменениях. Отдельные staging- и production-окружения
не запущены, поэтому сравнить их фактические настройки пока нельзя.

Тест использует контролируемые HTTP-ответы вместо настоящих GitHub/Stack Exchange;
их доступность и ограничения не измеряются. БД стенда временная, а Kubernetes
использует постоянный том; DNS, ingress, TLS и балансировка кластера в этот прогон
не входят. CI запускает тестовое окружение на GitHub runner и не развёртывает
приложение в Docker Desktop. Частота релизов и участие разработчика в эксплуатации
относятся к организации работы и не следуют только из конфигурации pipeline.

### XI. Журналирование

**Смысл.** Приложение формирует поток диагностических событий в стандартном выводе.
Сбор, маршрутизацию и хранение этого потока организует среда запуска.
[Описание фактора XI](https://12factor.net/ru/logs).

**Реализация.** Сервер использует SLF4J и консольное журналирование Spring Boot.
`LinkMonitorService` пишет идентификатор проверенной ссылки и результат,
`LinkUpdaterScheduler` — ошибки прохода мониторинга, обработчик исключений —
ошибки доступа к данным. В проекте не настроены файловые журналы приложения,
их ротация или зависимость от каталога логов. Уровень вывода задаётся `LOG_LEVEL`.

При прямом запуске сообщения видны в терминале, в Compose — через
`docker compose logs -f app`. Скрипт `verify-local.sh` перенаправляет вывод
запущенных процессов в файлы временного проверочного окружения. Это действие
оболочки, которая запускает приложение; сам сервер продолжает писать в консоль.

**Оценка: реализован.** Журналы можно собирать средствами контейнерной платформы
без изменения серверного кода. Таблица `link_updates` имеет другое назначение:
это сохраняемая пользователю история отслеживаемых ресурсов, а не технический
журнал работы процесса. Её наличие в PostgreSQL не нарушает данный фактор.

### XII. Административные задачи

**Смысл.** Разовые операции обслуживания запускаются отдельными процессами
из того же релиза, с теми же зависимостями и доступом к нужному окружению.
[Описание фактора XII](https://12factor.net/ru/admin-processes).

**Реализация.** Административные задачи проекта — применение миграций Liquibase
и назначение владельца ссылкам из существующей базы.
Сервис `migrate` использует тот же образ и подключение к PostgreSQL, что и `app`.
Он получает `MIGRATIONS_ENABLED=true`, `SCHEDULER_ENABLED=false`,
`SPRING_MAIN_WEB_APPLICATION_TYPE=none` и `APP_MODE=migrate`.
Liquibase применяет изменения при инициализации, затем `ScrapperApplication`
закрывает Spring-контекст и процесс заканчивает работу.

Compose ждёт готовности БД, затем успешного завершения миграции. Обычный сервис
`app` получает `MIGRATIONS_ENABLED=false`. При ошибке миграции условие запуска
`service_completed_successfully` не выполняется. SQL и журнал Liquibase находятся
в ресурсах приложения и поставляются вместе с JAR.

При прямом запуске используется отдельная команда:

```bash
APP_MODE=migrate MIGRATIONS_ENABLED=true SCHEDULER_ENABLED=false \
  SPRING_MAIN_WEB_APPLICATION_TYPE=none \
  java -jar scrapper/target/scrapper.jar
```

До её выполнения нужно экспортировать переменные подключения к БД, как описано
в README. Одного `APP_MODE=migrate` недостаточно: он отвечает за завершение
контекста, остальные свойства управляют миграциями, веб-сервером и планировщиком.

Для Kubernetes та же операция описана отдельным Job в `k8s/migrate.yaml`.
Гайд требует дождаться его успешного завершения перед применением web и worker:
порядок запуска обеспечивает процедура развёртывания.

`APP_MODE=assign-legacy` запускает другой разовый процесс того же JAR. Он получает
`LEGACY_OWNER_EMAIL`, находит существующий аккаунт и в транзакции назначает ему все
ссылки с `owner_id=NULL`. При конфликте URL операция не выполняется. Веб-сервер,
планировщик и миграции при этом отключены; после задачи контекст закрывается.
Для Kubernetes предусмотрен отдельный `assign-legacy.yaml`. Команды в README
и гайде используют конфигурацию БД того же окружения. Локальная проверка подтвердила
миграцию схемы 1.0.0, сохранение ссылки без владельца и её явное назначение.

**Оценка: реализован для имеющихся административных задач.** Миграция выполняется
разовым процессом того же приложения, а её файлы отслеживаются вместе с кодом в Git.
Работа Kubernetes Job ещё требует проверки в кластере.

## Ограничения

- Вход и разграничение доступа реализованы. Подтверждения email, восстановления
  и смены пароля, административных ролей и ограничения попыток входа в приложении
  пока нет. Compose публикует сервис на `127.0.0.1`; для публичного доступа нужны
  HTTPS, `SESSION_COOKIE_SECURE=true` и ограничение частоты входа/регистрации на прокси.
- Обновление с версии без входа требует остановки старых процессов перед миграцией.
  Старый сервер после миграции нельзя запускать: он не проверяет владельца.
  Существующие ссылки назначаются аккаунту явно; инструкция находится в README.
- Мониторинг обнаруживает увеличение временной отметки ресурса. Отдельное событие
  для каждого коммита, issue, ответа или комментария не гарантируется.
- Первая успешная проверка устанавливает исходную отметку; предшествующие изменения
  в ленту не попадают.
- Доступность и лимиты внешних API влияют на проверки. Ошибка сохраняется в
  `last_error`, ссылка и последняя успешная отметка остаются в БД. Автоматическая
  повторная попытка назначается не раньше чем через пять минут.
- Проверка удерживает блокировку одной строки во время внешнего HTTP-запроса.
  Редактирование или ручная проверка занятой ссылки могут вернуть HTTP 409.
  Такое устройство рассчитано на небольшую учебную коллекцию.
- Выпуск автоматизирован, нагрузка и жизненный цикл проверены в CI. Сам Kubernetes,
  rollout/rollback, постоянное окружение и длительные нагрузки ещё не проверены.
  Секреты конкретного развёртывания создаёт и сохраняет оператор.

Архитектура позволяет применять все 12 факторов. Технической невозможности выполнить
какой-либо из них нет. Открытые условия связаны с эксплуатацией, хранением конфигурации
конкретного развёртывания и проверкой кластера; они не объявляются неприменимыми к учебному проекту.

- 19 unit-тестов и 10 интеграционных тестов прошли без ошибок и пропусков.
  Проверены URL, мониторинг, пароль и BCrypt, уникальность email, CSRF, вход/выход,
  смена ID и срок сессии, изоляция CRUD/истории, ограничения БД и блокировки.
- 56 HTTP-проверок прошли на двух контейнерах одного образа с общей PostgreSQL 16.4.
  Проверены frontend и health, регистрация/вход, приватный CRUD, ответы ошибок,
  мониторинг обоих сервисов, защита от дублей, изменение URL, общая сессия
  и прекращение доступа на втором сервере после выхода через первый.
- Миграция временной PostgreSQL выполнена отдельным контейнером того же образа.
- Compose прошёл `config --quiet`; генератор создал шесть Kubernetes-манифестов,
  успешно разобранных YAML-парсером. Это проверка файлов, а не запуск кластера.
- Два worker обработали восемь ссылок: оба процесса участвовали, наблюдалось два
  параллельных обращения к HTTP-fixture, каждое изменение записалось один раз.

**Условия нагрузки.** GitHub runner: Ubuntu 24.04.5, x86_64, 4 CPU, около 15,6 GiB
памяти; Docker 28.0.4. Каждый web: 1 CPU, 768 MiB памяти, Java heap до 256 MiB,
пул БД пять соединений. Общая PostgreSQL 16.4, контролируемый внешний HTTP-fixture.
Каждый клиент имеет отдельный аккаунт и одну ссылку. Вход и регистрация происходят
до измерения, сессии и CSRF используются в запросах. Прогрев — 5 с, каждая точка —
20 с. 70% операций читают список, 20% — историю, 10% изменяют ссылку. Клиент
отправляет следующий запрос после ответа без паузы (closed-loop), сохраняет
HTTP/1.1-соединения и распределяет запросы между репликами по очереди.

| Web-реплик | Клиентов | Запросов | Запросов/с | p50, мс | p95, мс | p99, мс | Ошибок |
|---|---|---|---|---|---|---|---|
| 1 | 4 | 6 360 | 317,47 | 4,78 | 67,26 | 72,41 | 0 |
| 2 | 4 | 7 952 | 397,53 | 5,43 | 45,66 | 54,20 | 0 |
| 1 | 16 | 12 454 | 622,46 | 14,04 | 71,25 | 78,49 | 0 |
| 2 | 16 | 16 982 | 848,79 | 13,08 | 52,93 | 64,07 | 0 |

p95 означает, что 95% измеренных запросов завершились не медленнее указанного времени.
Всего 43 748 запросов, ошибок нет. При 16 клиентах добавление второй web-реплики
увеличило измеренную пропускную способность примерно на 36%, при 4 — на 25%.
Это один короткий сравнительный прогон, без статистической оценки повторяемости.
Он подтверждает работу нескольких процессов в данных условиях, но не гарантирует
такую скорость при больших коллекциях, другой машине или произвольном потоке запросов.

**Жизненный цикл процессов.**

| Сценарий | Результат |
|---|---|
| Четыре старта web до readiness | 11,533; 12,577; 11,849; 11,174 с |
| SIGTERM web без активного запроса | 0,230 с, код 143 |
| SIGTERM web во время запроса с задержкой API 3 с | 3,092 с, запрос завершён успешно |
| Сессия после перезапуска | Сохранена и принята другой JVM |
| SIGKILL web с незавершённой транзакцией | 0,158 с, код 137; частичного события нет |
| Повторная проверка на второй реплике | 0,124 с; состояние обновлено, дубля при повторе нет |
| SIGTERM одного из двух worker при фоновой работе | 0,281 с, код 143 |

Старт измеряется от `docker start` до readiness, завершение — от отправки сигнала
до окончания контейнера. Коды 143 и 137 соответствуют SIGTERM и SIGKILL.
Время повтора после аварии не включает ожидание завершения задержанного fixture-запроса.
Скрипт проверяет согласованность данных и успешный повтор, а не автоматический
перезапуск убитой реплики оркестратором. Все временные контейнеры удаляются в конце.

Дополнительно при функциональной проверке версии 1.1.0 на Java 25 и локальной
PostgreSQL 14.19 проверены браузерный вход/выход и миграция со схемы 1.0.0:
ссылки сохраняются без владельца, скрыты от новых пользователей и назначаются
аккаунту отдельной командой `assign-legacy`. Эти проверки не заменяют тестов
контейнерной версии, перечисленных выше. Рабочая БД не изменялась.
